# D13 压测：先预测，后测量

> **规矩：预测写下来之后不许改。** 测完再解释，人会把任何数字都说成"合理"；
> 先写死预测，差得远才会去追为什么 —— 差得远的那一项就是这次真正学到的东西。

基线：2026-09-09 内存版（MemStore），`-c 50 -P 16 --threads 4`，**825K QPS**（三次 845K/822K/937K，波动 ±10%）

## 预测（王吉星，2026-09-15，测量前）

| 命令 | 预测 QPS | 相对内存版 | 理由（他的原话） |
|---|---|---|---|
| SET | ~165K | **掉 5 倍** | "都是内存操作，但我的更简单，RocksDB 考虑的内容较多，所以会略慢" |
| GET | ~40K | **掉 20 倍** | "还在内存层就差不多；从磁盘读就是 IO 操作，慢好多倍" |
| DEL | ~40K | 同 GET | — |

**他对 RocksDB 的理解（测量前）**：有内存层和磁盘层，积累到一定程度才同步到磁盘。

## 实测（2026-09-15）

**参数**：`-n 500000 -r 1000000 -d 100 -c 50 -P 16 --threads 4`（DEL 用 `-n 200000`，每轮先灌 50 万条）
**CPU 核对**（note 21 ③）：cairn 90–94%（单线程，天花板 100% → 跑满）；redis-benchmark 15–45%（4 线程，天花板 400%）
→ **瓶颈在服务器，数字可信**
**落盘**：3 个 SST，97MB —— 超过 64MB memtable，GET 确实读到了磁盘

| | MemStore | RocksDB | 代价 |
|---|---|---|---|
| SET | 221K/249K/285K → **~250K** | 71.3K/73.9K/73.9K → **~73K** | **掉 3.4 倍** |
| GET | 499K/499K/498K → **~499K** | 83.1K/142.2K/79.8K → **~83K** | **掉 6.0 倍** |
| DEL | 398K/398K/399K → **~398K** | 61.3K/53.2K/47.0K → **~54K** | **掉 7.4 倍** |
| SET p50 | 1.0 ms | 3.5 ms | |
| GET p50 | 1.1 ms | **9.1 ms** | |
| DEL p50 | 1.0 ms | **12.6 → 16.2 ms** | |

## 结论

**预测对照：1 准 / 1 半对 / 1 错**（2026-09-15 修订——初版写成"三个方向全对"，是看到结果之后才定的宽松标准，属于评分本身犯了"先测后编标准"的错）

| | 预测 | 实测 | 判定 |
|---|---|---|---|
| SET | 掉 5 倍 | 掉 3.4 倍 | **准**。但理由"都是内存操作"只对一半——主因是 WAL 的 `write()` **系统调用**（陷入内核），不是普通内存拷贝 |
| GET | 掉 20 倍 | 掉 6.0 倍 | **半对**。"比 SET 掉得多""走磁盘更慢"对；按"全部走磁盘"估，实际是混合命中（memtable + block cache + SST） |
| DEL | "和 GET 一样" | 掉 7.4 倍 > GET 的 6.0 倍 | **错**。DEL = `Get` + `Delete` 两次操作，必然比 GET 慢。给过提示（"你的 del 干了几次操作"）未采用 |

⚠️ 下面两个"发现"是 Claude 从贴出的输出里读出来的，不是他自己注意到的。他做的是把命令跑对、输出完整贴出。

**两个实测挖出来的发现：**

1. **DEL 三次一路下滑 61.3K → 53.2K → 47.0K** —— 每轮前都灌 50 万条，库变大 → SST 层数增多 → 每次 Get 翻的层数增加。
   **这就是 LSM 的读放大，实测到了。** 数据量涨，读性能降。
2. **`top` 里偶尔 110.9% / 114.0%** —— 单线程 cairn 不可能超 100%，超出部分是 **RocksDB 后台 compaction 线程**。

**方法论教训（这次踩的）：**
- 第一轮 `redis-benchmark` 不加 `-r`，**所有请求打同一个 key** → GET 全程命中 memtable 最上层，"只掉 2 倍"是假象
- `DEL k` 的 `k` 从没被 SET → `del` 全走 `get` 未命中，`Delete` 一次没执行，测的根本不是 DEL
- 三个命令报出完全相同的 QPS（796812.81 ×3）= note 21 ① 的签名，撞天花板
- 第二块命令没带 `cd`，`Exit 127`，对着不存在的服务器测了 28 秒 370% CPU

**简历一句**：
> 对同一套网络层做内存后端与 RocksDB 后端对照压测：写吞吐 250K→73K，读 499K→83K，读延迟 p50 从 1.1ms 升到 9.1ms；观察到随数据量增长 DEL 吞吐从 61K 降到 47K，是 LSM 读放大的直接体现。
