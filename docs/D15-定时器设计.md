## 需求

**定期删除过期 key**：每隔 100ms，从所有 key 里随机采样 20 个，删掉已过期的。
（Redis 的真实做法。不能等 key 被访问才删——**没人访问的过期 key 会永远占着内存**。）

## 约束

**不能阻塞事件循环。** 睡 100ms 期间，连接进来了要能立刻处理。

## 矛盾点在哪

```cpp
// EventLoop.cpp:11
poller_->poll(-1, active_channels_);
              ↑ timeout = -1，【无限等待】
```
**没有任何网络事件时，`loop()` 卡在这一行不动，可以卡一整天。**

## 已否决的方案

### ❌ 方案 A：把 `poll(-1)` 改成 `poll(100)`，后面跟一段删除过期

**方向是对的（Redis 的 `aeProcessEvents` 就这么干），但两种写法各有一种病：**

```cpp
// 写法一：无条件在 poll 后执行
poll(100);  处理事件();  删除过期();
→ 压测时每秒几十万事件，poll 几乎立刻返回，循环转得飞快
→ 【删除过期每秒被调用几十万次】——性能灾难

// 写法二：只在超时返回时执行
int n = poll(100);
if (n > 0) 处理事件(); else 删除过期();
→ 事件密集时 poll 从不超时
→ 【删除过期永远跑不到】
```

> **根因：用「poll 返回了」当触发条件，但它跟「过了 100ms」不是一回事。**
> 正确的判据只能是**时间本身**：记住上次执行的**绝对时刻**，每轮问一句"真的过了 100ms 吗"。

**另外两个问题**：① 多个定时任务时 timeout 填谁？（得取最近的 → 需要数据结构）
② `timeout` 是 `Poller` 的参数，但"什么时候该干活"是定时器的知识不是 Poller 的——**硬编码 100 进 `loop()`，加第二个定时任务就得改 `loop()`。**

### ❌ 方案 B：信号中断（`SIGALRM` + `setitimer`）

**他自己的担忧"会影响真实业务"是对的，所以服务器里基本没人这么用。** 死在四点：

1. 信号处理函数里**只能调 async-signal-safe 的函数**，`malloc` / `printf` 都不行——想在里面删 key？删不了
2. 信号会**打断阻塞的系统调用**：`epoll_wait` 返回 `-1` 且 `errno == EINTR`（note 7），每处都要额外处理
3. 信号是**进程级**的，多线程时哪个线程收到不确定
4. 同种信号在处理期间再来会**合并成一个**，会丢

### ⚠️ 顺带纠正一个前提错误

他问过"怎么判断是不是有业务在工作"——**这个前提不成立**：

> **单线程 Reactor 里，不存在"业务正在工作时定时器触发"这种情况。**
> 整个事件循环一个线程，同一时刻只有一件事在跑。
> **定时器回调和业务回调是【排队执行】的，不是并发的——所以不需要判断，也没有锁。**
>
> 代价：**定时器回调里不能干慢活**，干慢了整个循环都卡住。
> （Redis 的定期删除限制"每次最多 25% 的时间"，就是这个原因。）

## ✅ 已确定的方向：`timerfd`

```
timerfd_create()   →  给你一个 fd
timerfd_settime()  →  设定"100ms 后到期"或"每隔 100ms 到期一次"
到期时             →  这个 fd 变成【可读】
read() 它          →  读出一个 8 字节整数 = 距上次读，到期了几次
```

**于是定时器和网络连接变成了完全相同的东西：**

```cpp
Channel timer_channel(timer_fd, EPOLLIN);
timer_channel.setReadCb([]{ 删除过期(); });
loop.updateChannel(&timer_channel);
```

> **`loop()` 一行都不用改。`EventLoop` 甚至不知道有定时器这回事——它只看到"又一个 Channel 可读了"。**
>
> **这是 note 2「一切皆文件」真正发力的地方**：`timerfd` / `eventfd` / `signalfd` 是同一个套路——
> **把一件本来不是 IO 的事，包装成 fd 上的可读事件，好让 epoll 统一处理。**

⚠️ **他当时的卡点**：「单线程没法对这个 fd 单独等待」。
**纠正：它不需要单独等待。** `epoll_wait` 本来就是**一个线程同时等一整筐 fd**，往筐里再扔一个而已。

### `timerfd_settime` 的两个数（API 事实，2026-09-18 补）

```c
struct itimerspec {
    struct timespec it_interval;   // 周期：首次到期后，每隔多久再响一次
    struct timespec it_value;      // 首次到期：多久之后第一次响
};
struct timespec { time_t tv_sec; long tv_nsec; };  // 纳秒！100ms = 100'000'000
```

| `it_value` | `it_interval` | 结果 |
|---|---|---|
| 100ms | **0** | 100ms 后响**一次**就死 ← 这就是 `runAfter` |
| 100ms | **100ms** | 之后每 100ms 响一次，**内核自己重复，不用重新设** ← 这就是 `runEvery` |
| **0** | 任意 | **关掉**这个定时器（disarm），`it_interval` 写啥都没用 |
| 100ms | 5s | 首次和周期可以不一样 |

`flags` = `0` → `it_value` 是**相对**时间；= `TFD_TIMER_ABSTIME` → 是**绝对**时刻。
`old_value` = `NULL` → 不关心旧设置是什么。

## ✅ 刀 1 已结：数据结构（2026-09-20 讨论，09-25 落文件）

### 结论

```
有序容器，存 (绝对到期时刻 → 回调)
it_interval = 0，每次响完自己重设成「容器里最近的到期时刻」
```

| 操作 | 什么时候发生 | 无序链表 | 有序链表 | 红黑树 `map`/`set` | 小顶堆 |
|---|---|---|---|---|---|
| ① 插入 | 每次 `runAfter`；周期任务每次执行完还要再插一次 | O(1) | **O(N)** ❌ | O(log N) | O(log N) |
| ② 取最近 | 每次响完，要拿它去 `settime` | O(N) | O(1) | O(1) | O(1) |
| ③ 取出所有已到期 | 每次响 | O(N) | O(k) | O(k) | O(k) |
| ④ **删任意（取消）** | 用户取消定时器 | O(N) | O(N) | **O(log N)** | **O(N)** ❌ |

> **否掉链表的那一行是 ①** —— 插入是最频繁的操作（王吉星自己判断出来的）。
> **否掉小顶堆的那一行是 ④** —— 堆里删中间元素是 O(N)。**这是面试 ①×③ 的交叉考点。**
> `k` = 这一轮真正到期的个数，通常 1~2 个，与总数 N 无关。

### 为什么 ③ 是 O(k) 而不是 O(N)：有序的价值是「能提前停」

```
容器按到期时刻排序，now = 1000：

 [900] [950] [1000] [1200] [5000] [9999] ... 后面还有一百万个
  到期   到期   到期    ↑
                      1200 > 1000 → 没到期
                      【后面的一定更大，一定也没到期】→ 立刻停

 扫 4 个收工，跟 N 无关
```
**有序容器的价值不是「找得快」，是「扫到第一个不满足的就能确定后面全不满足」。**

### 两个模型（并排看，区别只有一处）

```
【模型一：固定 tick】  Redis serverCron        【模型二：按需】  muduo / libevent

▸ 启动                                        ▸ 启动
  settime(it_value=100ms, it_interval=100ms)     容器空 → settime(it_value=0) 不响
  设一次，之后再也不碰

▸ addTimer(延迟 d, 回调 cb)                    ▸ addTimer(延迟 d, 回调 cb)
  容器.insert(now()+d, cb)                       容器.insert(now()+d, cb)
                                                 if (新插的比原来最早的还早)
                                                     settime(it_value = 新的最早时刻)

▸ timerfd 响了                                 ▸ timerfd 响了
  read(fd)                                       read(fd)
  now = 现在几点                                 now = 现在几点
  ┌────────────────────┐                        ┌────────────────────┐
  │ 从头取出所有<=now的│        ←完全相同→      │ 从头取出所有<=now的│
  │ 逐个执行回调       │                        │ 逐个执行回调       │
  │ 周期任务重新插回   │                        │ 周期任务重新插回   │
  └────────────────────┘                        └────────────────────┘
  ← 完了，内核 100ms 后自己再叫                  settime(it_value = 新的最早时刻)
                                                 （容器空 → settime(0) 彻底不响）
```

> **区别一句话：模型一是【内核】决定什么时候叫醒你，模型二是【你自己】决定。**
> 「算 now、比较、执行」那一大段两边一模一样 —— 区别在**什么时候醒**，不在**醒了干什么**。

| | 模型一 | 模型二 |
|---|---|---|
| 没定时器时 | 照样每 100ms 醒一次，**空转烧 CPU** | **完全不醒** |
| 精度 | 最坏晚一整个 tick（100ms） | 要 10ms 就是 10ms |
| 醒来的次数 | 多，且大部分 k=0（白醒） | 只在真有活的时刻醒 |

**模型二的胜势不在「一次处理得快」，在「根本不白醒」。**
（精度这条决定了 A1 必须排在 Raft 前面 —— 心跳/选举超时对精度敏感，Redis 的清过期不敏感。）

### ⚠️ 两个正交的选择，别混成一个

|  | **存绝对时刻** | **存剩余时间（要减）** |
|---|---|---|
| **固定 tick** | ✅ Redis 就是这格 | ❌ 每轮给所有人 `-=`，多一轮 O(N) 的写，减错一次全盘歪 |
| **按需** | ✅ muduo 就是这格 | ❌ 根本不成立 —— `settime` 该填多少都算不出来 |

**「减」在任何一格里都不是必须的。**

### 越界担心的答案

`CLOCK_MONOTONIC` 从**开机**起算，不是 1970 起算。

```
int32 存毫秒 → 2^31 ms ≈ 24 天就溢出      ← Windows GetTickCount 49.7 天回绕，出过大量事故
int64 存微秒 → 2^63 µs ≈ 29 万年
int64 存纳秒 → 2^63 ns ≈ 292 年
```
muduo 的 `Timestamp` 就是一个 `int64_t` 微秒。

### 📌 王吉星在这一刀里踩过的七个误区（回顾时先盖住答案自测）

| # | 当时的想法 | 实际 |
|---|---|---|
| 1 | 每轮给所有定时器**减**掉过去的时间 | 存**绝对时刻**，插进去就永不改 |
| 2 | 模型一要减、模型二不用减 | **两个都不用减**。tick/按需 与 减/绝对时刻 是**两个无关的维度** |
| 3 | 按需模型是不是每个定时器一个 fd | **都是一个 fd**。一个 fd 顶 N 个定时器，这就是 `TimerQueue` 存在的理由（fd 受 `ulimit -n` 限制） |
| 4 | key 放回调函数 | key 放**到期时刻**。`std::function` 连 `<` 都没有，当不了有序容器的 key |
| 5 | `unordered_map` 也会排序 | 哈希表，**完全无序**。`unordered` 是字面意思 |
| 6 | 有序容器也得全扫 | **有序 = 到期的全挤在最前面** → 扫到第一个没到期立刻停 |
| 7 | 两个模型的区别是「在里面算 / 在外面算」 | 区别是**谁决定什么时候醒** |

### ⬜ 刀 1 剩的尾巴

> **两个定时器的到期时刻完全一样怎么办？** `std::map` 的 key 唯一，会吞掉后来的那个。

这就是 muduo 写成 `std::set<std::pair<Timestamp, Timer*>>` 而不是 `map` 的原因。

## ✅ 三个设计问题的最终答案

**前提：路 B 已定**（多个定时器 + 能取消）。

### ① 数据结构 —— 两个容器

```cpp
std::set<std::pair<Timestamp, TimerId>> timers_;   // 按【时刻】排序：回答"谁最早到期"
std::unordered_map<TimerId, Timer>      active_;   // 按【id】查找：回答"id=7 是哪个"
```

**同一批数据，两种查法 → 两个容器。** `timers_` 只放 (时刻, id) 很轻；`Timer` 本体（含 `std::function`）只在 `active_` 存一份。

**pair 的第二元素用 `TimerId` 而不是 muduo 的 `Timer*`：**

| | muduo `set<pair<Timestamp, Timer*>>` | cairn `set<pair<Timestamp, TimerId>>` |
|---|---|---|
| 打破时刻平局 | 靠指针地址唯一 | 靠单调 id 唯一 |
| 生命周期 | `Timer` 要 `new`，**三处要记得 `delete`** | 本体住在 `unordered_map` 里，**零 new/delete** |
| ABA 问题 | 有（地址会被复用），靠 `TimerId{Timer*, seq}` 两字段对抗 | **没有**（id 单调递增永不复用） |
| 拿旧 id 取消 | 需要 seq 比对 | `active_.find` 找不到就返回，天然安全 |

> ⚠️ **`std::set` 的 key 也是唯一的**（`multiset` 才允许重复）。能装下两个时刻相同的定时器，**靠的是 `pair` 的字典序比较**：先比 `Timestamp`，相等再比第二元素 —— 所以第二元素的职责是**打破平局**，必须保证唯一。

### ② 所有权 —— 走路 1：照抄 `Acceptor`，`TimerQueue` 不认识 `EventLoop`

```cpp
class TimerQueue {          // 和 Acceptor 同构：持有 fd + 持有 Channel + 一个容器
    FdGuard fd_;            // ← Acceptor 的 socket_ 同位
    Channel channel_;       // ← Acceptor 的 channel_ 同位
    TimerId next_id_ = 1;   // 0 留作「无效 id」哨兵
    std::set<...>  timers_;
    std::unordered_map<...> active_;
};
// main.cpp：
TimerQueue tq;
loop.updateChannel(&tq.getChannel());     // ← main 接线，和 acpt 那行一模一样
```

**为什么不要 muduo 的 `EventLoop* loop_`**：数一遍 `TimerQueue` 要干的事 —— 注册 Channel（启动时一次，main 做）、`timerfd_settime`（对自己的 fd 直接系统调用）、容器增删（纯内存）、Channel 的监听事件（永远只有 `EPOLLIN`，不用改）。**没有一件需要 `EventLoop`。**

muduo 需要 `loop_` 是为了**多线程**（`runInLoop` 把跨线程的 `addTimer` 扔回 IO 线程、`assertInLoopThread`）。**cairn 单线程，这份保险不用买 —— 将来真要，加一个指针是五分钟的事。**

### ③ 接口

```cpp
public:
    TimerId runAfter(Duration delay,    std::function<void()> cb);   // 一次性
    TimerId runEvery(Duration interval, std::function<void()> cb);   // 周期（首次也隔一个 interval）
    void    cancel(TimerId id);
    Channel &getChannel();
private:
    TimerId addTimer(Duration delay, Duration interval, std::function<void()> cb);  // 共用实现
    void resetTimerfd(Timestamp when);
    void resetTimerfdToEarliest();
    std::vector<Timer> getExpired(Timestamp now);
    void handleRead();
```

**`runAfter`/`runEvery` 是两行壳**：`addTimer(d, zero, cb)` / `addTimer(i, i, cb)`。
**不用默认参数糊成一个函数** —— `runAfter(100ms, cb, 100ms)` 调用点看不出意图，`runEvery(100ms, cb)` 一眼就懂。**函数名该说清意图，不该让调用方从参数里猜。**

**`runAt` 不做**：`runAfter` 内部就是 `now + delay`，`runAt` 目前没有使用场景，要时五分钟能加。

**时间源直接用 `std::chrono::steady_clock`，不自己写 `Timestamp` 类** —— 标准保证单调、永不被 NTP 校时调整（这就是「为什么不用 `system_clock`」的答案）。muduo 手写 `Timestamp` 是因为它写于 2010 年，`<chrono>` 还不存在。**别抄历史包袱。**

## ✅ 已实现：落地版与原设计的三处差异（2026-09-26）

> **设计文档写的和最后写出来的不一样，这很正常 —— 但差异必须记下来，否则下次读这份文档会被误导。**

### 差异①（最重要）：周期任务【原地更新】，不摘走再插回

**原设计**（我给的，照搬 muduo 的形状）：

```
getExpired(now)  →  把所有到期的从【两个容器都摘走】，返回 vector
执行回调
reset(expired)   →  遍历 vector，周期任务重新插回容器 + settime
```

**实际实现**（王吉星自己提出的）：

```
getExpired(now)  →  一次性的：从两个容器删掉
                    周期性的：【原地把 expiration 改成 now+interval，重新插回 timers_】
                    两种都拷贝一份进 vector 返回（拷的是【旧的】expiration）
执行回调
resetTimerfdToEarliest()  →  只剩 settime 这一件事
```

**差别在「周期任务在执行回调期间，还在不在容器里」：**

```
【原设计】回调里调 cancel(自己的 id)
    → A 已经被摘走，active_ 里没有它 → cancel 静默失败
    → reset 又把 A 插回去 → 🔴 A 被取消了但下个周期还会跑

【实际实现】回调里调 cancel(自己的 id)
    → A 还在两个容器里（只是换了位置）→ cancel 正常删除
    → ✅ 真的被取消了
```

> **这正是面试考点③「正在执行时被取消怎么办」。**
> **muduo 为这个场景额外维护了一个 `cancelingTimers_` 集合来打补丁；这个写法从结构上就不会出现该问题。**
> 这是整个模块里最值得在面试里讲的一点 —— **不是"我实现了定时器"，是"我的取消语义比参考实现干净，而且说得出为什么"。**

**⚠️ 代价（要诚实承认）**：`ans.push_back(t)` 必须在改 `expiration` **之前**，否则 vector 里拿到的是下一次的时刻，算延迟会算错。这个顺序是隐式约定，没有编译器能替你保证。

### 差异②：`reset()` 拆成只做一件事

原设计的 `reset(expired, now)` 管两件事（重新入队 + settime）。重新入队挪进 `getExpired` 之后，它只剩 settime，于是改名 **`resetTimerfdToEarliest()`** —— **名字只承诺它真做的事。**

### 差异③：用运行时检查代替 `assert`

```cpp
if (interval <= Duration::zero()) { fprintf(stderr, "..."); abort(); }   // 不是 assert
```

**理由**：本项目默认 Release（`-O3 -DNDEBUG`），**`assert` 会被删成空语句**（实测：`assert(1==2)` 之后照常往下跑）。而 `interval <= 0` 的后果是**死循环**（新插的元素 `now+interval <= now`，立刻又算已到期）——**死循环比崩溃难查十倍**，这道防线在线上构建里必须真实存在。

> **通用判据：这个检查失败时后果是什么？**
> 「继续跑会算错」→ `assert` 够用；**「死循环 / 内存损坏 / 静默写坏数据」→ 必须运行时检查 + abort。**

## ⚠️ 已知行为：取消最早的定时器后会有一次「空响」

```
timers_ = { {1000,A}, {5000,B} }，timerfd 已设成 1000
cancel(A)  →  timers_ = { {5000,B} }，【但 timerfd 还设着 1000，没人去改它】

t=1000  timerfd 响 → read 掉 8 字节 → getExpired(1000) 返回空
        → 执行 0 个回调 → resetTimerfdToEarliest() → settime(5000)
        行为完全正确，只是白醒了一次
```

### 实测确认（2026-09-26）

```cpp
TimerId id = tq.runAfter(2s, []{ fprintf(stderr, "★ 不该出现\n"); });
tq.runAfter(4s, []{ fprintf(stderr, "★ 4 秒到\n"); });
tq.cancel(id);                       // 立刻取消最早的那个
// handleRead 里临时加：fprintf(stderr, "[handleRead] 醒了，exp=%llu\n", exp);
```

```
[handleRead] 醒了，exp=1      ← t=2s：醒了，但【一个回调都没执行】，这就是空响
[handleRead] 醒了，exp=1      ← t=4s
★ 4 秒到
```

**「★ 不该出现」没有出现** → `cancel` 生效了；**但 t=2s 仍然醒了一次** → 空响确实存在，且无害。

**决定：不修。**

```
修的代价：cancel 里多两条分支（"取消的是不是最早的" + "容器空了要 disarm"）
          → 两条分支 = 两处可能写错的地方，而且在 cancel 这种容易出错的路径上
收益    ：任何时刻【最多只有一次】空响在路上（下一次 settime 会覆盖它）→ 趋近于零
```

> ⚠️ **理由要说「复杂度」，不要说「性能」。**
> 空响本身也要走一遍 `epoll_wait 返回 → read → settime`，和"修"的那次 `settime` 是同一量级 ——
> **说"代价高"会被追问「多高？测过吗？」。判据是【复杂度的增加】vs【收益】，不是【CPU】vs【收益】。**

**muduo 同样不修。** 面试价值在于：**知道它存在、且说得清为什么不修** —— 比不知道强，也比过度优化强。

> 🔁 **复习时重新提问（2026-09-26 他自己要求挂上的）**：
> ① 「空响」是怎么产生的？（不许看上面，自己讲一遍时间线）
> ② 为什么不修？理由要落在**复杂度**上，不是性能上。
> ③ 如果要修，`cancel` 里要多哪两条分支？其中「容器空了要 disarm」具体是哪个系统调用、参数填什么？
>    （disarm = `timerfd_settime` 时 `it_value` 全填 0，含义是「停用」，不是「0 秒后到期」）

## 🐞 实现期间的踩坑记录（面试可直接讲）

| # | 现象 | 根因 | 怎么定位的 |
|---|---|---|---|
| 1 | 启动即段错误 | `for (auto &t : timers_)` 里 `timers_.erase(t)` —— **`++it` 要读当前节点才能找到下一个，节点已被释放** | **ASan** 报 `heap-use-after-free`；正解是 `it = container.erase(it)`（erase 返回下一个迭代器，这就是它存在的理由） |
| 2 | `cancel` 静默失效 + 下次到期 `terminate` | `expiration` 同时存在 `timers_` 的 key 和 `active_` 里 `Timer` 的成员**两处**，只改了一处 → 配对 `erase` 删不掉 → 留下孤儿 → 下次 `active_.at()` 抛 `out_of_range` | 推演 + 构造「回调内 cancel 自己」的用例复现 |
| 3 | 真错误被当成虚假唤醒吞掉 | `if (n==-1 && (errno = EAGAIN \|\| errno == EINTR))` —— **单等号是赋值**。`\|\|` 结合更紧，整个条件退化成 `n == -1`，且 `errno` 被写成 1 | 写了 20 行最小程序实测。**`-Wall` 没报**：`-Wparentheses` 规则是「程序员额外加了括号就视为故意」，**那对括号正好关掉了唯一能救命的警告** |
| 4 | 返回垃圾 `TimerId` | `runAfter`/`runEvery` 忘了 `return` | 编译器 warning。**修法是配置而非自觉**：CMakeLists 加 `-Werror=return-type`，让这类必崩问题变成编译失败 |
| 5 | CPU 100% 的隐患 | `handleRead` 里漏了 `read` 那 8 字节 → **LT 下到期次数 >0 就一直报可读** | 用 `top` 的 **`S` 状态 + `TIME+` 累计值**判定（`%CPU` 是瞬时采样，`TIME+` 骗不了人） |

> **1、2、4 是同一类**：在一段代码里同时追踪「几个值各自在哪个时刻是什么」。
> **练法：修改容器之前，把之后要用到的值【全部】先存成局部变量，之后只用局部变量，不再碰迭代器。**

## 面试考点：「设计一个定时器」

**`timerfd` 只是其中一小块，而且经常不是重点。** 真正考的是四样：

| 考点 | 问什么 |
|---|---|
| **① 数据结构**（大头） | 小顶堆 / 有序 set / **时间轮** 怎么选？插入、取最近、**删除任意**各是什么复杂度？ |
| ② 和事件循环怎么配合 | `timerfd`（Linux） vs `epoll_wait` 的 timeout（跨平台）← timerfd 只出现在这里 |
| **③ 怎么取消定时器**（高频） | 怎么标识一个定时器？**正在执行时被取消怎么办？** id 复用的 ABA 问题 |
| ④ 时间源 | 为什么必须用 `CLOCK_MONOTONIC` 而不是 `CLOCK_REALTIME`？（后者会被 NTP 校时和用户改系统时间搞跳变） |

⚠️ **反直觉的一点**：muduo 用 `std::set` 而**不是** `priority_queue`——
**堆里删除任意元素是 O(N)**，而"取消定时器"要求能删中间的。**这个取舍就是 ①×③ 的交叉考点。**

大厂更爱问**时间轮**（Kafka、Netty 都用）：插入 O(1)、到期 O(1)，代价是精度受槽粒度限制。

> **能答到什么程度，取决于做到什么程度：**
> 只做最简版（一个 timerfd + 一个固定周期任务）→ 只能答 ②
> **做完整版（多定时器 + 能取消）→ ①②③ 都能答，而且是"我写过"不是"我背过"**
> **多花两小时把「取消」做进去，这道高频题就从"答得出"变成"答得深"。**
