> **这是一条完整的性能定位链路**（问题 → 三轮测量 → 每轮暴露的方法论问题 → 结论 → 决策变更），

## 0. 为什么要测：一个标注卡住了两个技术方向

`PROGRESS.md` 里 9/9 记着一行：

```
| -c 50 -P 16 --threads 4 | 998K（环境天花板） | 998K（同） |
                                ↑ 就这四个字
```

**后果**：9/16–9/26 期间，「多 Reactor」和「io_uring 网络层」都被以**「收益测不出来」**为由否决/降级。

**而「环境天花板」和「单核天花板」差一个词，结论完全相反：**

```
环境天花板 = 压测客户端 / WSL 网络栈的限制   →  加线程、换 IO 模型都【白做】
单核天花板 = 服务器单线程 CPU 饱和           →  多核【能突破】
```

> ⚠️ 同一个项目的另一份文档 `D13-压测预测.md:21` 里明明写着
> 「cairn 90–94%（单线程，天花板 100% → 跑满）→ **瓶颈在服务器**」。
> **两份文档结论相反，而我们照着错的那份排了十天计划。**

## 1. 第一轮：`top` 采样 —— 失败，但失败本身有信息

```bash
rtk top -b -d 1 -n 20 -p $(pgrep cairn) | grep cairn
```

```
797199  ...  S   0.0  ...  0:02.06 cairn
797199  ...  R  46.0  ...  0:02.52 cairn
797199  ...  S  49.0  ...  0:03.01 cairn
797199  ...  S   0.0  ...  0:03.01 cairn
```

**读不出结论。** 因为：

```
top -d 1 每秒采一次，而这次压测只跑了约 2 秒 → 只采到 2 个有效点
TIME+ 2.06 → 3.01 = 共 0.95 CPU 秒

若负载真持续 2 秒、期间就是 46–49%  →  环境天花板
若负载只持续约 1 秒、被劈在两个窗口  →  期间可能 90%+
【同一组数字，两种解释，结论相反】
```

> 📌 **方法论教训①：采样周期必须远小于被测现象的持续时间。**
> 持续时间不到采样周期的 10 倍，就要么**加长负载**（调大 `-n`），
> 要么改用**累计量**（`TIME+` / `ps -o times`）而不是**瞬时量**（`%CPU`）——
> **累计量不怕对齐。**

## 2. 第二轮：累计 CPU 秒 —— 拿到第一个硬结论

```bash
rtk ps -o times= -p $(pgrep -n cairn)      # 压测前 → 0
rtk redis-benchmark -p 6380 -t get -n 5000000 -r 100000 -d 100 -c 50 -P 16 --threads 4
rtk ps -o times= -p $(pgrep -n cairn)      # 压测后 → 4
```

```
5000000 requests completed in 4.51 seconds
throughput summary: 1,109,385.38 requests per second
cairn CPU：4 秒（ps 只给整数，真实值 3.01～4.99）
```

### 🔴 决定性事实：**1.109M > 998K**

**天花板撞得破，就不是天花板。** 这一条不依赖任何 CPU 估算。

```
CPU 中位估计：4 ÷ 4.51 = 88.7%
误差范围    ：67% ～ 100%（单线程封顶）
```

> 📌 **方法论教训②：`ps -o times=` 只给整数秒。** 负载跑 10 秒以上时误差可忽略，跑 2 秒就不行。

## 3. 第三轮：把分母找齐 —— 结论钉死

### 3a. 压测客户端自己吃了多少

```bash
rtk bash -c "time redis-benchmark -p 6380 -t get -n 5000000 -r 100000 -d 100 -c 50 -P 16 --threads 4 > /tmp/bench.txt 2>&1"
```
```
real 0m5.012s    user 0m1.386s    sys 0m10.250s
→ benchmark 消耗 1.386 + 10.250 = 11.636 CPU 秒 ÷ 5.012s = 232%（上限 400%，4 线程）
本轮 QPS：999,400（与上一轮 1.109M 相差 11%，属正常波动）
```

### 3b. ★ 关键的分母：**这台机器有 16 个核**

```bash
rtk nproc          # → 16     （AMD Ryzen 9 7940H，8 物理核 ×2 线程）
```

### 3c. cairn 的精确 CPU + 构成

```bash
rtk awk '{print "user jiffies:", $14, "  sys jiffies:", $15}' /proc/$(pgrep -n cairn)/stat
# → user jiffies: 182   sys jiffies: 709
```
```
user 1.82s + sys 7.09s = 8.91 CPU 秒
两次压测负载墙上时间 4.51 + 5.00 = 9.51s（其余时间空闲，几乎不耗 CPU）

8.91 ÷ 9.51 = 93.7%          ← 比第二轮的 88.7% 更准
且与第二轮的粗测互相印证（一次约 4 秒 × 两次 ≈ 8.9 秒）✅
```

## 4. 结论：三行数字，一起看才有意义

| | 实际用掉 | 它自己的上限 | 占比 |
|---|---|---|---|
| **cairn** | **0.94 核** | **1 核**（单线程） | **≈ 94%** ← 基本跑满 |
| redis-benchmark | 2.32 核 | 4 核（4 线程） | 58% ← 还有余量 |
| **整台机器** | 约 **3.2 核** | **16 核** | **20%** ← 几乎空着 |

> ### **瓶颈是「cairn 只会用一个核」，不是环境。**
> 998K 从来不是天花板，它只是**单核 cairn 的正常落点**（两次实测 999K / 1.109M，波动 11%）。

> 📌 **方法论教训③：看到任何 CPU 百分比，先问「分母是多少」。**
> 同样是「cairn 94% + benchmark 232%」，
> 在 **4 核**机器上是「机器快满了，加线程也抢不到核」；
> 在 **16 核**机器上是「机器才用 20%，随便加」。
> **是 `nproc` 那个 16 决定了结论，不是那两个百分比。**

## 5. `sys : user = 80 : 20` —— 一条线索，以及它**不能**推出什么

```
sys  709 jiffies (79.6%)      user 182 jiffies (20.4%)
```

**能推出**：时间主要花在内核里，不是花在 RESP 解析、哈希查找这些自己的代码上。

**不能推出**：「io_uring 能省下这 80%」。

```
sys 时间高  ≠  系统调用【次数】多  ≠  io_uring 能省下来      （三件事）

sys = 【进出内核的过路费】        +  【内核真正干的活：TCP 协议栈、数据拷贝、软中断】
           ↑ io_uring 能省这块          ↑ io_uring 省不掉，活还是要干

粗算：-P 16 下一次 read 捞 16 条命令、一次 write 发 16 条回复
     → 约 125K 次系统调用/秒 × 1–2μs = 0.12–0.25 核
     → 只占 cairn 那 0.94 核的 13%–27%，其余省不掉
```

> 📌 **方法论教训④：看到一个"开销很大"的数字，先问
> 「这笔开销里，我打算用的那个技术究竟能动哪一部分？」** 动不了的部分再大也不该算进收益。

**→ 这个问题只有原型能答，别再堆测量了。** 再测收益递减。

## 6. 决策变更

| 方向 | 原判 | 新判 | 依据 |
|---|---|---|---|
| **多 Reactor** | 存疑（"收益测不出来"） | ✅ **确定做，排在前面** | 单核 94% 饱和 + 12 个空闲核 → 收益确定且可测；机制会逼出 `eventfd` + `runInLoop`，Raft 也要用 |
| **io_uring 网络层** | 否决 | ⚠️ **排在多 Reactor 之后，不否决也不承诺** | "测不出差异"这条垮了；只剩"成本高（要重做 `Buffer` 所有权）"。做完多 Reactor 后基线变成多核，**那时再测信噪比更高** |
| **io_uring 文件 IO** | Raft 阶段 | ✅ 不变 | bridgeIM 那边实测确认没有文件 IO 落点 |

## 7. 这条链路本身的价值

**和 9/9 的 Nagle 那条一样，是一条完整的定位链路，而且这次还多了一层「推翻自己之前的结论」：**

```
现象      一个被标成"天花板"的数字，据此否决了两个技术方向
第一轮    top 采样 → 数据自相矛盾 → 发现采样周期 vs 负载时长不匹配
第二轮    改用累计量 → 撞破"天花板"（1.109M > 998K）→ 标注本身就是错的
第三轮    补齐分母（16 核）+ 精确到 /proc → 94% 单核饱和，整机只用 20%
结论      瓶颈在单线程，不在环境 → 两个技术方向翻案
```

**简历一句（备选）：**
> 排查吞吐瓶颈时发现原有的「环境天花板」结论未经验证：改用累计 CPU 量测后实测到 1.109M QPS（超出原记录 11%），
> 结合 `/proc/[pid]/stat` 与机器核数确认服务端单线程 CPU 94% 饱和而整机仅用 20%，
> 据此推翻「多核无收益」的判断，把多 Reactor 从待议改为确定项。

> ### ⚠️ 最大的教训（写给以后的自己）
> **凡是「到顶了 / 这是极限 / 再优化也没用」这类结论，都要问一句：**
> ## **「谁撞过？撞的那次数据在哪？」**
> 998K 被当成天花板用了 **17 天**，期间据此砍掉两个方向；
> **而第一次有人真去撞它，一下就超了 11%。**
> 没有那次数据，它就只是个假设，不能拿来砍需求。
