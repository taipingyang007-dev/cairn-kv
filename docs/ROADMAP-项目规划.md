## 已定的判断

### ❌ 不做的（连同理由）

| | 为什么不做 |
|---|---|
| **Qt / 全栈** | 市场在客户端/桌面/嵌入式 GUI，与 C++ 后端 + 游戏服务器岗无关。**"全栈"在校招是减分**——面试官第一反应是"哪个都不深"。机会成本 = 一个 io_uring 对比实验 |
| **堆功能**（文件传输/语音消息/语音转文字/短信登录） | 一半是接第三方 API，技术含量接近零。**培训班项目的卖点是"看起来完整"，不是"能被深挖"**。花两个月换简历上六行功能，面试深挖时能聊的还是老问题 |
| **eBPF / DPDK / 用户态协议栈** | DPDK 要特定网卡；eBPF 校招几乎不问。**而且"用户态协议栈"他手上的 cs144 就是教学版**——面试说"实现过 TCP 核心机制"，别说"做过用户态协议栈"（后者指 DPDK/f-stack 生产级，会被问穿） |
| **C++20 协程（秋招前）** | `promise_type`/awaitable 心智负担极大，2 周打不住 |

> **核心判据：校招看「一个点能挖多深」，不是「一共做了多少个点」。**

### ✅ 技术点落位 —— 标准是"这个项目有没有这个痛点"

| 技术 | 放哪 | 为什么是这个项目 | 成本 |
|---|---|---|---|
| **perf / 火焰图** | **cairn** | 已有压测负载，抓张图就能说"X% 时间花在 Y" | **半天**，性价比最高 |
| **差分测试** | **cairn** | 同一组命令跑 MemStore vs RocksDBStore 比结果。**兑现 2026-09-15 选"乙方案"（IStore 接口）的理由** | 半天 |
| **io_uring** | **cairn（文件 IO，不是网络层）** | ⚠️ **2026-09-26 修正**：原写"对比实验信噪比高"是**未经验证的推测**。真正的落点是 **Raft 日志持久化**（epoll 对普通文件完全无能为力），网络层那段降级待议 —— 见下方「io_uring 落位（09-26 重定）」 | 文件 IO 段随 Raft；网络层段 3–7 天且要重做 Buffer 所有权 |
| **协程** | **bridgeIM** | IM 到处是"发 RPC 等回复"的四层回调嵌套，**协程真的解决了痛点**；cairn 回调链短，用协程是"为了用而用"，一问就露 | 2 周+，秋招后 |

**io_uring 的真实难点**（不是 API，API 十来个函数半天学完）：
- 模型从**就绪通知**（内核说"可以读了"，你自己 read）变成**完成通知**（你说"帮我读"，内核说"读完了"）
- 核心机制：**用户态/内核态共享的两个环形队列**（SQ 提交 / CQ 完成）→ 批量提交 N 个请求只要一次系统调用
- ⚠️ **最大的坑：缓冲区生命周期**。epoll 下 `read` 返回时 buf 就能用；io_uring 下提交后 **buf 必须一直有效到完成事件回来** → 直接冲击 `Buffer` 的设计，所有权的思考方式要换一遍
- 环境已具备：内核 6.6 ✅，`apt install liburing-dev` 即可

### bridgeIM 该往哪走 —— 不是功能，是这五个

| | 面试官会问 | 为什么值钱 |
|---|---|---|
| **消息可靠投递** | "网络断了这条消息去哪了？" | **IM 的技术核心**：离线消息、ACK、去重幂等、消息顺序 |
| **分布式 ID** | "消息 ID 怎么全局有序？" | 雪花算法 / 号段，必问 |
| **服务注册发现** | "一个服务挂了怎么办？" | 微服务第一课 |
| **Redis + MySQL 一致性** | 穿透/击穿/雪崩、延迟双删 | **bridgeIM 是这族问题的原生现场，cairn 是硬加** |
| **连接管理** | "10 万连接怎么维持？" | 心跳、重连、连接↔用户映射 |

**这五个一个 UI 都不用写，深度超过那个 1.8 万行的培训项目。**

⚠️ **bridgeIM 重构的第一价值不是加协程**。他自述"当时水平差、很多知识没理解"——那它缺的是**现在这套理解**（边界、所有权、回调生命周期、签名设计）。
**顺序：先用新理解把它捋一遍，再加协程。** 否则是在自己都没理解的东西上盖楼。

### io_uring 落位（2026-09-26 重定）

| 落点 | 状态 | 依据 |
|---|---|---|
| **Raft 日志持久化**（12–1 月） | ✅ **确定做** | epoll 对普通文件**完全无能为力**（普通文件永远"可读"）；Linux 上异步文件 IO 只有线程池 / 难用的 POSIX AIO / io_uring 三条路；Raft **必须落盘才能回 ack**；优化点是**批量提交**，正是 io_uring 强项；etcd / TiKV 都在这块死磕 |
| **网络层**（epoll 版 vs io_uring 版并存） | ⚠️ **排在多 Reactor 之后，不否决也不承诺** | 见下 |
| **bridgeIM** | ❌ **没有落点**（2026-09-26 那边实测） | 离线消息走 `RPC → MySQL` 一条一行，在线消息不持久化；唯一的文件 IO 是日志，`fputs + fflush` 一行一次、0 次 fsync、无批量。**没有真实场景，硬加会被一眼看穿** |

**网络层那段的正反证据（2026-09-26 实测，见 `docs/D16-瓶颈实测.md`）：**

```
支持：cairn 的 CPU 构成是 sys 709 : user 182 jiffies = 【80% 在内核里】
      → 系统调用开销是大头，而 io_uring 正是专门省系统调用的

反对：① sys 时间 ≠ 系统调用次数 ≠ io_uring 能省下来，这是三件事
        sys = 【进出内核的过路费】(io_uring 能省) + 【内核真正干的活：TCP栈/拷贝】(谁都省不掉)
        粗算：-P 16 下约 125K 次系统调用/秒 × 1–2μs = 0.12–0.25 核
             只占 cairn 那 0.94 核的 13%–27%，其余省不掉
      ② 成本被低估：io_uring 提交后 buf 必须一直有效到完成事件回来
        → 【直接冲击 Buffer 的所有权模型】，不是 3–7 天能干净做完的
```

> **决定：先做多 Reactor。** 做完之后基线从"单核 1M"变成"多核 N M"，**那时再测 io_uring 网络层，信噪比比现在高得多**。
> **而且这个问题只有原型能答，别再堆测量了** —— 再测下去收益递减。

**为什么 Raft 日志是 io_uring 不可替代的地方**（2026-09-15 他追问"找一个真正需要它的地方"）：
- Raft 规则：收到 `AppendEntries` **必须落盘才能回 ack**，否则崩溃即丢数据、一致性垮掉
- **epoll 对普通文件完全无能为力**（普通文件永远"可读"）；Linux 上异步文件 IO 历史上只有线程池或难用的 AIO
- 这是**他自己写的代码**，不藏在 RocksDB 内部
- 优化点是**批量**：多个 entry 一次 `io_uring_submit`，正是 io_uring 的强项
- etcd / TiKV 都在这块死磕 → **"为什么这里用 io_uring"有现成答案，不是为用而用**

### ❌ 自己写 LSM —— 不做

2–4 周，而且跟 RocksDB 是**替代关系不是叠加**（写了等于把 RocksDB 换掉，不增深度）。玩具版被问到 compaction 策略 / 崩溃恢复边界 / bloom filter 误判率三问见底。
**同目的、1/10 成本的替代：读 LevelDB 源码**（约 1.5 万行，RocksDB 的祖先，代码干净）。"我读过 LevelDB 的 memtable 和 compaction 实现"比"我写了个玩具 LSM"站得住——能对着工业代码讲细节。**排在 Raft 之后，当八股深化。**

### 为什么 io_uring 放 cairn 而不是 bridgeIM

bridgeIM 也是高并发网络服务，**适合是适合，差在准备度**：

| | cairn | bridgeIM |
|---|---|---|
| 压测基线 | ✅ 六组数字 | ❌ |
| 验收套件 | ✅ 29 项 | ❌ |
| 网络层抽象 | ✅ 亲手拆的 Poller/Channel/Connection | ⚠️ 自述"当时没理解透" |
| 加上去等于 | 第二个实现 | 在没理解透的东西上盖楼 |

另：**io_uring 和协程都动网络层**，都塞 bridgeIM 会搅在一起，讲的时候分不清是谁的功劳。

### ❌ 用同一把尺子否掉的（记下来，免得反复纠结）

| 不做 | 它解决什么 | 为什么 cairn 不该加 |
|---|---|---|
| **内存池 / 对象池** ⚠️**有条件** | 高频创建销毁**同样大小**的小对象时，`malloc/free` 的开销 + 内存碎片 | cairn 的 `Connection` 生命周期长（keep-alive）不是高频；`Buffer` 扩容后复用；唯一真实分配点是每条命令的 `std::string reply`。**但实测 `user` 只占 20%（80% 在内核）→ 全省掉天花板也只有那 20% 的一部分**。<br>**→ 解除条件：先做 perf 火焰图，图上 `malloc` 真是热点再考虑。现在加，面试问"省了多少"你没数字** |

### 排序的四条判据（比清单本身重要）

1. **面试官只深挖 2–3 个点。** 项目价值 = 最深的那几个点有多深，**不是覆盖了多少功能**。
   → 直接推出：加命令是广度不是深度，降级；定时器 / 过期 / 缓存层各自是一个完整的设计题，升级。
2. **依赖关系决定顺序，价值决定取舍。** 定时器 → 过期；定时器 → Raft；`IStore` → `CachedStore`。
   价值再高，依赖没到就得等。
3. **deadline 是硬约束。** 9 月是 HC 最充足的月份，投递窗口不等人 → 简历 / README / 八股优先于任何代码。
   **而且简历 bullet 写的过程会自己暴露缺口**，比事先列清单准。
4. **证据链完整 > 功能完整。** 一个有压测数字 + 对照实验 + 踩坑记录的功能，胜过五个「我实现了」。
   → `DESIGN.md` 原话：**全部价值在于「面试官指着任何一层，你都能聊 20 分钟，聊的是自己踩过的坑」。**
