### 21. 压测方法论 🟢 2026-09-09

**① 样本太小，测的是计时器不是服务器**
`-n 1000` 时 SET/GET 都报 `34482.76`（小数点后两位完全相同）= `1000/0.029`，两个测试落进同一个计时刻度。加到 `-n 100000` 才稳定。

**② 一次测量不算数据**
出现过 `rps=-3151.39`（负吞吐）。**物理上不可能的值 → 先怀疑测量，别怀疑被测物。**（WSL2 时钟跳变，吞吐 = 请求数 ÷ 耗时，耗时算成负数。）至少跑三次看区间。cairn 三次：845K / 822K / 937K —— **波动本身就有 ±10%**，"快 5%"没有意义。

**③ 先看 CPU 再看 QPS**
> **压测工具 CPU 跑满、被测服务没跑满 → 你测的是压测工具的上限，不是服务器的能力。**

实测两次都撞上这个：`redis-benchmark 96% / cairn 77%`。解法：`--threads N` 加客户端线程。加到 4 之后两边同撞 ~998K（环境天花板），这时**比吞吐已无意义，该比"同吞吐下谁烧的 CPU 少"**。

**④ 对比实验的价值全在变量控制**
- ❌ 拿 Docker 里的 Redis 当基线：`-p 6379:6379` 多一层 NAT 转发，对手被平白拖慢
- ✅ 装原生 `redis-server`，且 `--save '' --appendonly no` 关掉持久化（cairn 不落盘，不关就是"纯内存"比"内存+落盘"）
- **面试官一句"你俩跑在同样的环境里吗"就能把没控变量的数字全部作废。**

**⑤ 结论要诚实，诚实的结论更值钱**

最终数据（同机同参数 `-c 50 -P 16 --threads 4`）：

| | cairn | 原生 Redis 7.0.15 |
|---|---|---|
| 吞吐（环境天花板） | 998,004 | 998,004 |
| p50 | 0.663 ms | 0.727 ms |
| 每百万请求 CPU | 0.932 核秒 | 0.982 核秒 |

```
❌ "我的 KV 比 Redis 快"                    ← 问一句 CPU 就崩
✅ "cairn 每条命令做的事少得多（不查过期/类型、不发键空间通知、不管 AOF/RDB、
    只支持 6 个命令），在功能砍到这个程度的前提下只省 5% CPU，还在噪声内。
    结论不是我更快，是 Redis 的单命令开销已经压得非常低，我没有性能优势。"
```

**大多数简历只有最后一行数字，有完整定位链路的才值钱**：现象 → 排除法（CPU）→ 探针实测 → 根因 → 两处修复 → 前后数字 → 与工业实现的差距。
