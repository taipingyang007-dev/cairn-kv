### 1. 客户端凭什么认你 —— 协议是唯一契约 🟢 2026-09-02

**一句话**：网络两端唯一的契约是字节格式（协议）。客户端认协议不认程序。

- `redis-cli -p 6380` = 拨电话：和 127.0.0.1 的 6380 端口建 TCP 连接。谁在**那个端口**上 `listen()`，内核就把连接交给谁。**全程没有任何身份验证环节。**
- 敲 `PING` 后发生的事：redis-cli 把它编码成 `*1\r\n$4\r\nPING\r\n`（14 字节）发出 → 傻等对面回字节 → 收到 `+PONG\r\n`（7 字节）→ 按 RESP 解码（`+` 开头 = 简单字符串）→ 打印 `PONG`。它的判断依据**只有字节**。
- v0 和真 Redis 的全部关系 = `main.cpp:54` 那 7 个字节恰好和真 Redis 回 PING 的字节一模一样。没有注册、没有认证、没有"接入生态"。
- v0 靠**装傻**混过去：敲 `SET a b` 也回 PONG——答非所问，但客户端无法察觉。整个项目 = 把"不管问啥都说 PONG"逐步换成"问啥真的答啥"（RESP 解析器 → 存储层 → …，即七个毛病）。
- 推广：浏览器 ↔ nginx（HTTP）、mysql 命令行 ↔ MySQL 服务器，全是同一模式。

**我的复述**（2026-09-02，原话存档）：redis-cli 走的是 RESP 格式协议；连接不确认对端身份，端口上有 `listen()` 就能连上；收到的数据只要符合 RESP 就解析打印。

### 9. COMMAND DOCS 卡死之谜 —— v0 唯一的一次 read 被握手抢走 🟢 2026-09-03

**实测事实**：交互模式 `redis-cli` 在连接建立的瞬间发 `*2\r\n$7\r\nCOMMAND\r\n$4\r\nDOCS\r\n`（26 字节，向服务器讨命令文档做提示/补全），**同步等回复，收到回复才打印提示符**。一次性模式只发命令本身。

| 时刻 | redis-cli | v0 |
|---|---|---|
| ① | connect 发起握手 | 阻塞在 accept |
| ② | 握手完成（内核） | accept 返回 client_fd → read 阻塞 |
| ③ | **立刻发 COMMAND DOCS，等回复** | 26 字节到达 → **read 被唤醒返回 26** |
| ④ | 等 | 不看内容，write `+PONG\r\n` |
| ⑤ | 收到 +PONG，RESP 解析成功 → **打印提示符** | close ×2，**进程退出** |
| ⑥ | 敲 PING → 发向已死连接（本侧 CLOSE_WAIT，v0 侧 TIME_WAIT）→ 收到 RST → 报 `Server closed the connection` → **自动重连** → 6380 没人听 → 正常系统 refused，**WSL mirrored 卡死** | 已不存在 |

**填空**：你的服务器把 **redis-cli 的开场白（COMMAND DOCS）** 当成了 **这个客户端唯一的一条请求**，还把它当 PING 回了 PONG，然后下班。

- **毛病 1 的完整病历**：不是"只服务一个客户端"，是"**只服务一个客户端的一条消息**"——循环 accept 和循环 read **缺一不可**。
- **+PONG 答非所问为什么不报错**：格式合法就解析，**客户端认协议不认内容**（条目 1 闭环）。连接层的拒绝/丢弃和 RESP 无关，两层别串。
- **实验卫生**：实验前 `rtk pgrep -a a.out`，有残留 `rtk pkill a.out`（今早 REUSEPORT 实验留了个卡在 accept 的 v0，害我在假象上推理了一轮）。"只收不回"的 python 假服务器是抓客户端开场白的利器。

**我的复述**（2026-09-03，原话存档）：redis-cli 在连接成功之后直接发送一个 COMMAND DOCS，v0 收到之后离开 read 阻塞返回 26，进入 write 返回 +PONG，客户端收到后由于 RESP 解析成功认为连接成功、打印了提示符，但 v0 已经进入两个 close 了。

### 16. RESP 回复类型与 redis-cli 的显示 🟢 2026-09-06

| 回的字节 | redis-cli 显示 | 类型 |
|---|---|---|
| `+PONG\r\n` | `PONG`（无引号） | 简单字符串 |
| `$5\r\nhello\r\n` | `"hello"`（**带引号**） | 批量字符串 |
| `$-1\r\n` | `(nil)` | 空值——GET 不存在的 key 必须回它 |
| `:1\r\n` | `(integer) 1` | 整数 |
| `*0\r\n` | `(empty array)` | 数组 |
| `-ERR xxx\r\n` | `(error) ERR xxx` | 错误 |

- **引号是"对了"的证据**：redis-cli 给批量字符串加引号，好让你看出 `"  "` 和 `""` 的区别。客户端靠**第一个字节**就知道这是哪种东西。
- **每条回复都必须以 `\r\n` 结尾**——漏了客户端会一直等，**连接卡死**（2026-09-06 实际踩到）。
- **命令名大小写不敏感**：用 `||` 列举拼法是死路（`Ping`、`pInG` 认不出），统一 `ToUpperCopy` 一次再比。但**错误信息里要回显用户敲的原文**，不是转大写后的。
- **命令处理的固定三步**：① 校验参数个数 → `-ERR wrong number of arguments for 'xxx' command` ② 操作存储 ③ 按 RESP 生成回复。
- **if-else 现在是对的起点**：毛病 5 的原文就是"命令加到第 8 条，if-else 一百行"→ 那时才抽分发表。**现在提前抽表，是在抽一个还不知道形状的东西。**

### 22. 命令分发表：把 if-else 变成数据结构 🟢 2026-09-09

**为什么要换掉 if-else 链**（三条都能被验证）：

1. **重复的校验必然长出不一致** —— 4 处 arity 检查曾经说着两种话（3 处漏了命令名）。**同一逻辑手抄 N 遍，N 越大走样概率越接近 1。**
2. **程序不知道自己支持哪些命令** —— `COMMAND` 只能返回空数组，**不是偷懒是做不到**：`if` 链是**控制流**，程序没法遍历自己的 `if` 语句。
   > **判据：需要被遍历、计数、查询的东西，必须是数据结构，不能是代码结构。**
3. **没地方挂元信息** —— 将来做 EXPIRE / 主从 / AOF，每条命令都要标"读还是写"。

**（性能上的 O(n) 次字符串比较也是真的，但对 20 个命令排在这三条后面。别把性能当第一个理由——它在这里最弱。）**

**结构**：

```cpp
using CommandHandler = std::string (*)(const std::vector<std::string>&, MemStore&);
struct Command { int arity; CommandHandler handler; };
static const std::unordered_map<std::string, Command> kCommands = { {"GET", {2, get}}, ... };
```

- **`struct` 是"表的一行"，`map` 是"整张表"** —— `map<K,V>` 的 `V` 只能放一个东西，可一行有好几列，所以要 struct。
- **`unordered_map` vs `map`**：先问"需不需要有序"。哈希表 O(1) 平均，**最坏 O(n)（哈希冲突全挤进一个桶，桶里是链表）**；红黑树 O(log n) 但有序。**B+ 树是磁盘结构**，全部设计目标是减少磁盘 IO 次数，内存里用它没意义。
- **函数名会自动退化成函数指针**，表里直接写 `get` 即可，不用 `&`，更不用中间变量。
- **`arity` 用正负号编码**（真 Redis 的办法）：`>0` = 恰好 N 个，`<0` = 至少 |N| 个。**所以类型必须是 `int` 不能是 `size_t`——无符号装不下负数。**

**踩到的两个坑**：

- 🔴 **有符号 / 无符号比较**：`arity < args.size()` 中 `int` 会被转成无符号，`-3` 变成 `18446744073709551613`，**负 arity 的校验完全失效**。`SET k` 被放行 → `args[2]` 越界 → **整个服务器崩溃退出**。`-Wextra` 的 `-Wsign-compare` 会警告。**判据：绝不让有符号数和无符号数直接比较。**
- 🔴 **比较方向反了**：`arity<0` 表示"至少 N 个"，报错条件是**参数太少**（`args.size() < |arity|`），写成 `|arity| < args.size()` 就是"太多才报错，太少放行"。

**两条要一起记的**：

- **`std::vector::operator[]` 不做边界检查** —— 越界是未定义行为，可能崩、也可能读到垃圾继续跑（更可怕）。`at()` 会抛 `std::out_of_range`。
  > **判据：下标由外部输入决定时，要么用 `at()`，要么把进入前的范围校验做到绝对可靠。** 选了后者，那个校验就是唯一防线，错了就直接崩。
- **重构必须有验收，而且验收要能发现"新结构带来的新 bug"** —— 编译零警告、ctest 全过、前 11 条正常，**只有第 12 条 `SET onlyonearg` 把服务器打死了**。换表之后新犯的错（GET 指向 pingHandler、比较方向反了）**编译器一个都发现不了，类型完全合法**。
  > **在服务器代码里，健壮性 bug 比功能 bug 严重一个数量级**：功能错了用户重试一次，进程死了所有人一起下线。

**代码组织**（`.h` 只剩一行声明）：

| 东西 | 去处 | 判据 |
|---|---|---|
| `cmd::handleCommand` 声明 | `.h` | `main.cpp` 要调它，**唯一对外的东西** |
| `struct Command` / `using` / `kCommands` / 各 handler | `.cpp`，handler 全部 `static` | `main.cpp` 从不碰 |

> **一句话决策：改这一行，`main.cpp` 需不需要重新编译？需要 → 接口，放 `.h`；不需要 → 放 `.cpp`。**

- **同一个 `.cpp` 内部也能用前置声明解循环依赖**：`command()` 要用 `kCommands`，`kCommands` 要引用 `command` —— 把 `command` 的**声明**放表前面、**定义**放表后面即可。**和 `.h`/`.cpp` 分家是同一个机制，只是尺度不同。**
- **`.h` 不该 include 自己不用的东西**——头文件的 include 会**传染**给所有调用方（一个 `<string>` 就是 3 万行）。
- **重构时行为一个字节都不许变**：`COMMAND` 一度被改成返回 `integer(kCommands.size())`，属于同时改结构又改行为，出问题分不清是哪边。**先跑绿，新功能单独做。**
