# ① Nagle × 延迟 ACK

> **定位并修复 Nagle 算法 × 延迟 ACK 的病态交互：pipelining 下吞吐不升反降（55.7K → 18K QPS），经 `TCP_NODELAY` 与回复批量写两处修复提升至 825K**

**钩子**：「不升反降」——反常识，面试官一定会问机制。
**为什么不用「45 倍」当钩子**：那会让人先怀疑你的基线有多烂。**你要的是好奇，不是怀疑。**

### Q1「掉了三分之二，你怎么确定是 TCP 层，不是你代码里有 bug？」

**排除法 + 正面证据，两半都要给：**

```
第 1 步  看 CPU   cairn 4% / 压测工具 4%
         → ★「慢」有两种：干得慢(CPU 满) / 等得久(CPU 空)
         → 代码再烂也烂不出 4% 的 CPU  →  排除算力问题

第 2 步  等什么   磁盘 IO？当时是 MemStore，纯内存，没磁盘
                  锁？单线程 Reactor，没有锁
                  → 只剩网络层的某个等待

第 3 步  测延迟   min 42.04 / p50 44.01 / max 47.86 ms
         ★ 先看 min：本机 loopback 该是【微秒级】，42ms 慢了 180 倍
                     → 连最快的一次都这么慢 = 不是偶发，每次都被拖
         ★ 再看 max−min：只差 14%  → 每次拖的量【一样多】
         → 判据：算得慢，延迟随负载变；等定时器，延迟是常数
         → 常数延迟 = 有人在等定时器 → 40ms 正好是 TCP_DELACK_MIN
```

⚠️ **措辞**：不要说"这也算我的代码 bug"。正确说法是——
**"Nagle 和延迟 ACK 都是 TCP 标准行为，不是 bug。根因在我的应用层产生了小包序列（每处理一条命令就 write 一次），根因在我的代码，症状表现在 TCP 层。"**
（区分【根因】和【症状】，比笼统认错专业。）

### Q2「825K……那你比原生 Redis 还快？」

> "**并不是。** 同参数（`-c 50 -P 16 --threads 4`）下两边都撞到环境天花板 998,004。
> 同吞吐下 cairn 每百万请求烧 0.932 核秒、Redis 0.982——**只省 5% CPU，还在噪声内**（三次测量本身就有 ±10% 波动）。
> 而我每条命令做的事少得多：不查过期、不查类型、不发键空间通知、不管 AOF/RDB，只支持 6 个命令。
> **在功能砍到这个程度的前提下才省 5%，结论不是我更快，是 Redis 的单命令开销已经压得非常低，我没有性能优势。**"

> **有数据的诚实 >> 没数据的谦虚。**

### Q3「只关 Nagle 行不行？只做批量写行不行？」

```
只关 Nagle      →  小包满天飞，浪费带宽；16 条命令可能真的发出接近 16 个报文段
只做批量写      →  ★【半包一来就失效】：一次 read 只拿到 8 条，
                    解析完 send 一次 → 第二次 read 补齐后再 send 一次
                    → 第二个包"前一个未被 ACK 且不满 MSS" → 又被扣住 40ms
                 而半包是 TCP 的常态，不是异常
两个都做        →  既保证一次发出的报文段够大，又不给 Nagle 发作的机会
```
（加分：**大响应**同理——GET 返回 100KB，切成几十段，**最后那个不满 MSS 的尾巴段会被扣住**。）

### Q4「把 Nagle 关掉，放到生产环境有什么风险？」

⚠️ **代价 ≠ 风险。代价是你知道且接受的成本；风险是可能在你不知情时爆掉的东西。**

```
代价：小包变多 → 带宽浪费、包数量上去、网卡中断和软中断(top 的 si)跟着涨
      本机/局域网无所谓，【跨公网才是真成本】

★ 风险（面试官要听的）：
  TCP_NODELAY 依赖一个【隐式前提】——应用层自己负责合并。
  现在 send() 在 while 循环【外面】，所以关得起。
  哪天有人重构时把 send() 挪进循环，16 个小包就真的会飞出去 16 次——
  而且【不报错、29 条验收全绿】，因为数据一个字节没错，只是慢了。
  ★ 正确性测试抓不到性能退化。
```

### Q5「这个坑只有 Redis 这种协议会踩吗？举个别的例子」

**先给三条件，再套例子：**
```
① 一端产生【连续的小包序列】
② 另一端【此刻无数据可发】   ← 全部关键在这
③ Nagle + 延迟 ACK 都开着
```

**最经典的例子，连 pipelining 都不需要：一条逻辑消息被拆成多次 write。**
> HTTP 服务器 `write(header)` 然后 `write(body)`：header 小包先飞出去，body 被 Nagle 扣住；
> **对端拿到的是半条消息，应用层没法回应** → 它也没数据可发 → 延迟 ACK 等 40ms。

其他成立的：RPC 框架批量调用后逐个返回小结果、游戏服务器高频小状态更新、SSH/telnet（Nagle 当年就是为它设计的）。

⚠️ **不要举"打开网站"**：HTTP/1.1 的 pipelining 浏览器基本都禁用了，而且网页响应通常很大，不是小包序列。
⚠️ **游戏服务器要说准**：它关 Nagle 的真实理由是**延迟敏感**（多 40ms 玩家能感觉到），是预防性地一律关掉，不是等三条件凑齐。

# ② IStore 抽象

> **抽象 `IStore` 接口支持内存 / RocksDB 两种存储引擎运行时切换，协议层与命令层零改动**

**钩子**：「零改动」。

### Q「真的零改动？怎么保证的？」

> "cmd 层的函数签名只认 `IStore&`，不认任何具体实现。
> `grep -rn "MemStore\|RocksDBStore" src/cmd/` → **0 条**，可以当场验证。"

### Q「为什么要留两个实现？测完删掉一个不就行了？」

⚠️ **"为了对比所以保留"是个假理由——实验做完就能删。**
**正确判据：删掉它，我会损失什么？**

```
MemStore 删掉会损失：
  ① 验收测试的运行环境：29 条验收跑内存版，【不用清 data/ 目录】，不受 compaction 干扰
  ② 开发时的快速迭代：改协议层后立刻验证，不用等 RocksDB 打开、回放 WAL
  ③ 排查 bug 的隔离维度：先在 MemStore 上复现——【不复现就说明问题在存储层】

★ 一句话：MemStore 不是对照组，它是【测试这个用户】天天在用的东西。
```
（同一条判据也用在 io_uring：留 epoll 版不是"为了对比"，是内核兼容 + 抽象边界的证据 + 对比数字讲得出。）

# ③ 受控对照压测

> **设计受控对照压测量化持久化代价：同参数下 SET / GET / DEL 分别下降 3.4 / 6.0 / 7.4 倍，并从 DEL 连续三轮衰减（61K → 47K）实测到墓碑累积引发的读放大与 compaction 开销**

**钩子**：「受控对照」和「三轮衰减」。

### Q「你控制了哪些变量？」

> "同一台机器、同一套 29 条验收、同一组压测参数（`-n 500000 -r 1000000 -d 100 -c 50 -P 16 --threads 4`），
> **只改一个命令行参数切换存储——变的只有那个父类指针指向谁。**
> 而且先看 CPU 确认瓶颈在服务端（cairn 90-94% 单线程跑满、压测工具 15-45%）才采信数字。"

> **测量的可信度来自变量控制，不来自数字好看。**

### Q「为什么 DEL 掉得最多？」

> "我的 DEL 实现是**先 Get 判断存在性再 Delete**，成本 ≈ GET + SET，比两者都贵。"

### Q「为什么 SET 掉得最少？」

> "**SET 只写不找**——顺序追加 WAL + 写内存 memtable，返回 OK 时 SST 里还没有这条数据。
> **GET 要沿 memtable → immutable → L0 → L1… 一层层找**，可能读好几次磁盘。
> **写只写，读要找**，这才是根源。"

### Q「三轮衰减说明什么？墓碑为什么引发读放大？」

⚠️ **不是"遇到墓碑会变慢"**（找到墓碑就返回，那个动作不慢）。

> "**墓碑不是读的时候碍事，是它让数据变多了。**
> 墓碑是新数据不是删除 → 数据总量增长 → memtable 更快写满 → flush 更频繁 → **L0 文件变多**
> → 每次 Get 要翻更多 L0 文件（读放大上升）→ 同时触发 compaction，后台抢 CPU 和磁盘带宽 → 前台吞吐掉。
> `top` 里 cairn 超过 100% 的那部分就是 compaction 线程。"

**加分：三个放大是一个环，不是三个独立指标**
```
墓碑堆积 → 空间放大↑ → 文件变多 → 读放大↑ → 触发 compaction → 写放大↑ + 抢资源 → QPS↓
```
> "那三个数字（61.3 → 53.2 → 47.0）就是这个环转了三圈的痕迹。"
